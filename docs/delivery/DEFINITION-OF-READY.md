# Definition of Ready

A task should not enter implementation until all relevant items below are clear.

## Requirement
- [ ] Desired behavior is stated.
- [ ] Actor/user is known.
- [ ] Acceptance criteria are testable.
- [ ] Non-goals are clear enough to prevent scope creep.

## UX / behavior
- [ ] Happy path is defined.
- [ ] Error/empty/loading/permission states are defined when relevant.
- [ ] Important edge cases are listed.

## Contracts and data
- [ ] API/event contract impact is understood.
- [ ] Data model/migration impact is understood.
- [ ] Backward compatibility expectations are known.

## Security/privacy
- [ ] Authn/authz behavior is defined.
- [ ] Sensitive data implications are known.
- [ ] Abuse/rate/tenant risks are considered where relevant.

## Verification
- [ ] Expected unit/integration/E2E tests are known.
- [ ] Manual acceptance steps are known when automation is not appropriate.

## Delivery
- [ ] Dependencies/blockers are identified.
- [ ] Task is small enough for a focused reviewable change.
