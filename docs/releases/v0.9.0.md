# Vibe Coding Production Kit v0.9.0

VCP v0.9.0 turns the project from a copy-once engineering kit into a **versioned development system with a safe lifecycle**.

The key change is `vcp update`: initialized repositories now carry enough state to distinguish VCP template changes from project-local decisions, preview migrations, merge independent edits, stop on conflicts, recover from failed updates, and keep future releases upgradeable.

## Highlights

### Safe lifecycle state

`vcp init` now creates:

```text
.vcp/
├── manifest.json
└── baselines/
```

The manifest tracks the installed VCP version, install profile, managed paths, ownership policy, baseline hashes, baseline locations, modes, and template versions.

Once initialized, VCP refuses to replace lifecycle state with `init --force`. Use the update engine instead.

### Check, preview, then apply

```bash
vcp update . --check
vcp update . --dry-run
vcp update .
```

Machine-readable forms are available with `--json`.

When npm reports a newer VCP than the currently running CLI, VCP returns a version-pinned `npx` command targeting the repository that was actually checked. An older CLI never pretends it can safely apply templates/migrations from a newer release.

### Explicit update plan

The planner classifies paths as:

```text
NOOP
ADD
UPDATE
MERGE
RENAME
DELETE
ADOPT
DETACH
PRESERVE
IGNORED
CONFLICT
```

Any `CONFLICT` blocks the apply phase before project-file writes.

Managed files that disappear from a target package without an explicit migration removal become `CONFLICT`; packaging mistakes are not treated as permission to delete user files.

### Ownership-aware behavior

VCP separates:

- `managed` files — safe refresh/merge when possible;
- `generated` adapters — local + upstream edits become conflicts;
- `preserve` project decisions — customized PRD/architecture/security documents are preserved;
- explicitly ignored paths — detached from VCP management without deleting local content.

Use:

```bash
vcp manage ignore AGENTS.md
vcp manage track AGENTS.md
```

### Bounded three-way merge

For mergeable files VCP compares:

```text
baseline
local project file
target VCP template
```

Independent changes can merge automatically. Overlapping changes become conflicts. The merge algorithm has a bounded work limit so large files fall back to manual resolution instead of consuming unbounded memory.

Final-newline changes are treated as real three-way changes rather than being silently normalized away.

### Versioned migrations

The update engine includes an ordered migration registry for version-to-version changes. Renames and removals must be declared explicitly, and chained migrations compose across multiple historical versions.

SemVer comparison includes prerelease precedence while ignoring build metadata as required for precedence decisions.

### Transactional apply and recovery

Apply follows:

```text
lock
→ plan
→ backup
→ transaction state
→ stage
→ apply
→ rebuild baselines
→ write manifest
→ verify
→ commit state
```

Planning happens **after acquiring the lifecycle lock**, preventing a second updater from planning against stale state.

If apply fails after backup creation, VCP attempts automatic rollback.

### Conservative rollback

```bash
vcp rollback .
```

v0.9 restores the newest safe recovery point, or the backup tied to an interrupted transaction.

Arbitrary historical partial backups are intentionally rejected because later updates may have changed additional managed paths that an older partial backup cannot reconstruct safely.

### Lifecycle-aware Doctor

`vcp doctor` now checks:

- VCP manifest state;
- project/CLI version relationship;
- baseline integrity;
- corrupt lifecycle state;
- interrupted update transactions;
- the existing engineering-system checks for docs, commands, CI, and plan/review workflow.

### Shared locking and path safety

Update, rollback, and manage mutations share the same lifecycle lock.

Managed paths and `.vcp` internal paths reject traversal and symlink escapes. Dead locks on the same host can be reclaimed safely; fresh foreign-host locks remain protected until the stale interval.

## Existing workflow retained

v0.9 keeps the existing production workflow:

```text
init
→ task
→ ready
→ context
→ implement
→ verify
→ independent review
→ doctor
→ release / observe
```

and adds the lifecycle loop:

```text
update --check
→ update --dry-run
→ update
→ doctor
```

## Notes for the first public release

Before npm publication, the CLI can be executed directly from GitHub:

```bash
npx --yes github:MoeEyani/Vibe-Coding-Production-Kit init . --agent all --stack auto --yes
```

After npm publication:

```bash
npx vibe-coding-production init . --agent all --stack auto --yes
```

## Toward v1.0

The next priorities are feedback-driven rather than feature-count-driven: framework/monorepo profiles, Git-aware review/release automation, domain security profiles, prompt evaluation, architecture fitness functions, and an extensible profile/plugin model.

The v0.9 goal is narrower: make the current system **safe to adopt and safe to evolve** before asking users to depend on it.
